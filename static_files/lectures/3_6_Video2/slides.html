How Live Streaming Works

Live Streaming

  • We can upload and host videos using a streaming protocol
    • A Video on Demand (VOD) service
  • What about live streaming?
    • The video doesn't exist yet when viewers start watching
    • Segments are created while the streamer is streaming
  • Most live streaming isn't truly live
    • There will be several seconds of delay in the stream
    • Acceptable loss to gain reliability and scale

The Pipeline

  • Typical setup (eg. Twitch/YouTube Live/etc.)
  Streamer (OBS)
        │   RTMP: rtmp://localhost:1935/live + stream key
        ▼
  Ingest server
        │   Converts the stream to HLS: A playlist + segments
        ▼
  Web server  (Your app)
        │   HTTP: Normal GET requests for the playlist and segments
        ▼
  Viewers (hls.js)
  • Viewers never talk to the ingest server

RTMP

  • Real-Time Messaging Protocol
    • Runs over TCP. Default port 1935
    • The streamer pushes a continuous stream of video and audio to the server
  • Streaming software (OBS, ffmpeg, phones, consoles) speaks RTMP
  • Browsers don't
    • Viewers need HLS, served over HTTP
    • HTTP also works with caches and CDNs, which is how big platforms reach millions of viewers
  • RTMP is used for ingest: Getting the stream into your system

The Ingest Server

  • Receives RTMP streams and turns them into HLS
    • Writes a playlist and segments to disk for each stream
    • Keeps updating them as long as the stream is live
  • Asks your app whether each stream is allowed
  • For the HW, you don't write this
    • Use the tiangolo/nginx-rtmp image
    • Same idea as using the postgres image instead of writing a database
  • Your job is everything around it
    • Stream keys, deciding who can stream, serving streams to viewers, the front end

The Ingest Server

nginx.conf

  • The ingest server is configured with an nginx.conf file
  • Copy it into the container at /etc/nginx/nginx.conf
events {}
rtmp {
    server {
        listen 1935;
        application live {
            live on;

            # Called when a stream starts and ends
            on_publish http://app:8080/api/live/start;
            on_publish_done http://app:8080/api/live/end;

            # Write each stream as HLS to /hls/{stream_key}/index.m3u8
            hls on;
            hls_path /hls;
            hls_nested on;
        }
    }
}

on_publish

  • When a streamer connects, the ingest server sends a POST request to your app
  • The body is url-encoded
    • Same format as the HTML forms from HW2
    • Several fields. name is the stream key the streamer entered
POST /api/live/start HTTP/1.1
Host: app:8080
Content-Type: application/x-www-form-urlencoded

app=live&...&call=publish&name=f3a9c2e17b4d80a65e2f1c9d3b7a4e08&type=live
  • Respond 200 OK to allow the stream
  • Respond 403 Forbidden to reject it. The ingest server disconnects the streamer

on_publish

// POST /api/live/start (Called by the ingest server)
form := parseURLEncoded(request.Body)          // Your code from HW2
user, found := findUserByStreamKey(form["name"])
if !found {
    sendResponse(connection, 403)              // Reject: Streamer is disconnected
    return
}
addLiveStream(user, form["name"])              // Track active streams
sendResponse(connection, 200)                  // Allow the stream
  • Any stream key that doesn't belong to a user must be rejected
  • on_publish_done sends the same format when the stream ends
    • Remove the stream from your active streams
  • Multiple streams can start at the same time
    • If you track active streams in memory, protect them with a mutex

Who Calls These Endpoints?

  • The ingest server, not a browser
    • No Same-Origin Policy or CORS concerns
  • Anyone can still send requests to them
    • An attacker could send name=<guess> to check whether a stream key is valid
    • With at least 80 bits of entropy, guessing is hopeless
  • Never trust the request to identify a user by anything other than the stream key

Live Playlists

  • Live HLS playlists change while you watch
    • New segments are added every few seconds
    • Old segments are removed from the playlist and deleted
    • No #EXT-X-ENDLIST until the stream is over
  • The player re-requests the playlist every few seconds to find new segments
#EXTM3U
#EXT-X-VERSION:3
#EXT-X-MEDIA-SEQUENCE:41
#EXT-X-TARGETDURATION:5
#EXTINF:5.000,
41.ts
#EXTINF:5.000,
42.ts
#EXTINF:5.000,
43.ts

Live Playlists

  • Caching: The playlist changes every few seconds
    • Your caching headers from HW1 might cause browsers to reuse an old playlist
    • Send Cache-Control: no-store for live playlists
  • Segments never change once written
    • Caching them is fine
  • One rendition per stream
    • Whatever quality the streamer sends. No ABR for this HW

Why the Delay?

  • The ingest server can't write a segment until it has several seconds of video
  • The player downloads a few segments before it starts playing
    • So it doesn't stall if the next segment is slow
  • Plus the time to encode, upload, and download
  • Result: Viewers are commonly 10-30 seconds behind the streamer
    • Don't panic if your stream takes a while to appear
  • If that delay is unacceptable (eg. Video calls)
    • Use UDP instead of TCP, skip the segments, accept dropped packets
    • More on this with WebRTC

Multiple Containers

Three Containers

  • Your app now has three services
    • app: Your Go server. Port 8080
    • db: Your database
    • ingest: nginx-rtmp. Port 1935 for streamers
  • docker compose up must start all three
services:
  app:
    build: .
    ports:
      - "8080:8080"
  ingest:
    build: ./ingest    # Has a Dockerfile and nginx.conf
    ports:
      - "1935:1935"
    depends_on:
      - app
  db:
    image: postgres
    # ...

The Ingest Container

  • Build the ingest image from its own Dockerfile in a subdirectory
  • Start from the nginx-rtmp image and add your config
ingest/
├── Dockerfile
└── nginx.conf
FROM tiangolo/nginx-rtmp
COPY nginx.conf /etc/nginx/nginx.conf
  • build: ./ingest in your compose file

Startup Order

  • nginx looks up the hostname app when it starts
    • If your app's container doesn't exist yet, the ingest server fails
  • depends_on starts your app's container first
  • depends_on doesn't wait until your server is ready
    • Your Go server starts quickly, so this is usually fine
  • For more assurance, add a healthcheck to your app and use condition: service_healthy
    • The same pattern you may have used to wait for your database

Docker Volumes

Containers Have Their Own Files

  • Each container has its own filesystem
  • The ingest server writes streams to /hls in the ingest container
    • Your app can't see them
  • Files written inside a container are lost when the container is recreated
    • docker compose up --force-recreate
    • Uploaded avatars and videos disappear
  • We need storage that lives outside the container

Volumes

  • A volume maps storage outside the container to a directory inside the container
  • Mount the same storage into two containers and they share the files
  • Bind mount: A directory on your machine (./hls)
    • You can see the files on your machine. Great for debugging
  • Named volume: Storage managed by Docker (uploads)
services:
  ingest:
    volumes:
      - ./hls:/hls                  # Host ./hls appears at /hls in ingest
  app:
    volumes:
      - ./hls:/app/hls              # Same host directory, appears at /app/hls in app
      - uploads:/app/public/uploads # Named volume for avatars and videos
volumes:
  uploads:

Volume Gotchas

  • --renew-anon-volumes deletes anonymous volumes when testing and grading
    • Bind mounts and named volumes persist
  • A volume hides what the image had at that path
    • Mount ./uploads at /app/public and your front end disappears
    • Mount only the directories that hold uploaded or streamed files
  • Directories must exist before you write to them
    • Create them in your code at startup (eg. os.MkdirAll)
  • Don't submit uploaded videos or HLS files with your HW
    • Your code must still work when those directories start empty

Stream Keys

Stream Keys

  • A stream key is a secret that lets someone stream as a user
    • Anyone with the key can stream as that user
    • Treat it like a password
  • Every user gets their own key
  • Generate it randomly with at least 80 bits of entropy
    • Use crypto/rand. Never math/rand
keyBytes := make([]byte, 16)          // 128 bits
_, err := rand.Read(keyBytes)         // crypto/rand
streamKey := hex.EncodeToString(keyBytes)

Showing the Key

  • Only the owner may ever see their stream key
  • Show it somewhere obvious, like the settings page
    • Requires front end changes
    • Return it only to the logged in user it belongs to
  • Never include it in any response other users can see
    • eg. The active streams list, chat messages, user search
  • Unlike passwords, you can't store only a hash
    • You need to show the key to its owner
  • Real apps let users reset their key if it leaks

Don't Leak the Key

  • The ingest server names each stream's directory after its stream key
    • /hls/f3a9c2e17b4d80a65e2f1c9d3b7a4e08/index.m3u8
  • If you host that directory as-is, the key is in the URL of every playlist and segment
    • Visible in the Network tab of every viewer
    • Any viewer could stream as that user
  • The key must never appear in any URL, playlist, or segment path requested by viewers
  • Host each stream at a public path instead
    • eg. /live/{username}/index.m3u8
    • Your server maps the public name to the stream key

Serving a Stream

  • The playlist refers to segments by relative paths (41.ts)
    • The browser requests /live/{username}/41.ts
    • The key is never sent to the browser
// GET /live/{username}/{file}
username, file := parseLivePath(request.Path)
streamKey, live := activeStreamKey(username)   // Server-side lookup only
if !live || !isPlaylistOrSegment(file) {
    send404(connection)
    return
}
serveFile(connection, "hls/"+streamKey+"/"+file)
  • Only allow index.m3u8 and segment names
    • Path traversal applies here too
  • Viewers only ever connect to port 8080

The Front End

Watching Live Streams

  • Viewers need to find the streams that are live
    • Keep a list of active streams from on_publish and on_publish_done
    • Add an endpoint or page to list them
    • Or add them to the VideoTube list with an appropriate title
  • Playing a live stream is the same as playing any other HLS video
    • hls.js sees there is no #EXT-X-ENDLIST and keeps refreshing the playlist
const hls = new Hls();
hls.loadSource(`/live/${username}/index.m3u8`);
hls.attachMedia(videoPlayer);
  • When a stream ends, it must disappear from the list

Testing

Streaming with OBS

  • Settings → Stream → Service: Custom
    • Server: rtmp://localhost:1935/live
    • Stream Key: The key from your settings page
  • Or stream a video file with ffmpeg (Less fun)
ffmpeg -re -i video.mp4 -c:v libx264 -preset veryfast -c:a aac -f flv rtmp://localhost:1935/live/{stream_key}

Debugging a Stream

  • Follow the stream through the pipeline
  • Did the ingest server receive it?
    • docker compose logs ingest
  • Did your on_publish endpoint respond with a 200?
  • Are files appearing in ./hls/{stream_key}/ on your machine?
    • The bind mount makes this easy to check
  • Can you request the playlist from your app?
    • Correct MIME type? Cache-Control: no-store?
  • Is the stream in your active streams list?
