CORS and Other Web Attacks

Relaxing the Same-Origin Policy on purpose with CORS, plus login XSRF, clickjacking, XSS, and more layers of defense

Recap

Recap

  • XSRF: Another site makes your browser send a request, with your cookies attached
  • The SOP blocks cross-origin reads
    • Simple requests (Anything a form could send) are sent without asking
    • Non-simple requests are preflighted, and never sent without the server's permission
  • SameSite controls whether cookies are attached to cross-site requests
  • XSRF tokens protect every request that changes state, in every browser
  • Today: What if you want another origin to access your server?

CORS

Cross-Origin Resource Sharing

  • The SOP is sometimes too restrictive
    • You host a public API that other sites call from their front ends
    • Your front end is at cse312.com and your API is at api.cse312.com (Different origins!)
  • Cross-Origin Resource Sharing (CORS) lets a server relax the SOP for its own responses
    • The server approves preflights, and marks which origins may read its responses
    • Using Access-Control-Allow-* headers
  • CORS never makes anything stricter. It only allows things that the SOP would block

Preflight - Request

OPTIONS /api/posts/42 HTTP/1.1
Host: api.cse312.com
Origin: https://cse312.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: content-type
  • Origin - The origin of the page that wants to send the request
  • Access-Control-Request-Method - The method of the real request
  • Access-Control-Request-Headers - The non-safelisted headers the real request will include
    • Content-Type is listed here since application/json is not one of the 3 simple types

Preflight - Response

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://cse312.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type
Access-Control-Max-Age: 600
  • Access-Control-Allow-Origin must match the requesting origin (or be *)
  • The requested method and headers must be in the allowed lists
  • Access-Control-Max-Age - The browser can cache this approval for 600 seconds
  • The real response must also include Access-Control-Allow-Origin
    • Otherwise, the real request is sent, but JavaScript still can't read its response

Access-Control-Allow-Origin

  • Access-Control-Allow-Origin: https://cse312.com
    • JavaScript on https://cse312.com may read this response
    • Must be a full origin: protocol + host + port
    • Access-Control-Allow-Origin: cse312.com does not work
    • Only one origin is allowed in this header
  • Access-Control-Allow-Origin: *
    • JavaScript on any origin may read this response
    • Fine for truly public data (A public API, fonts, a CDN)

Allowing Multiple Origins

  • The header can only hold one origin. To allow several:
    • Read the Origin header of the request
    • If it's in your allowlist, echo it back in Access-Control-Allow-Origin
    • Add Vary: Origin so caches don't serve one origin's response to another origin
ALLOWED_ORIGINS = {"https://cse312.com", "https://www.cse312.com"}

origin = request.headers.get("Origin")
if origin in ALLOWED_ORIGINS:
    response.headers["Access-Control-Allow-Origin"] = origin
response.headers["Vary"] = "Origin"

Credentials

  • By default, a cross-origin fetch does not send cookies
    • fetch(url) uses credentials: "same-origin"
  • To send cookies cross-origin: fetch(url, {credentials: "include"})
    • The request is sent with cookies (Subject to SameSite)
  • For JavaScript to read the response to a request with credentials, the server must send:
    • Access-Control-Allow-Credentials: true
    • Access-Control-Allow-Origin with an exact origin
      • * is not allowed with credentials
  • This is why Access-Control-Allow-Origin: * cannot leak data that requires a logged-in user

CORS Is Not a Defense

  • CORS is enforced by the browser
    • Your server only states its policy
  • curl, Python's requests, and an attacker's own scripts ignore CORS entirely
    • They can send any request and read any response
    • But they don't have your users' cookies
  • CORS protects your users' browsers. It does not protect your server
    • Your server must still authenticate every request

CORS Misconfigurations

  • The dangerous configuration isn't *. It's this:
# DON'T: Trusts every origin, with cookies
response.headers["Access-Control-Allow-Origin"] = request.headers["Origin"]
response.headers["Access-Control-Allow-Credentials"] = "true"
  • Any site can now read any logged-in user's data from your API
    • And send any request, since every preflight is approved
  • Checking the origin carelessly is just as bad
    • origin.endswith("cse312.com") allows https://freemoney4you-cse312.com

Other Attacks

Login XSRF

  • Normal XSRF: Act as the victim on the victim's account
  • Login XSRF: Log the victim into the attacker's account
    • The attack page submits your login form with the attacker's username and password
    • The victim doesn't notice they're logged into someone else's account
    • Everything the victim does is saved to the attacker's account
      • Search history, uploaded files, a saved credit card number
    • The attacker logs in later and reads it all
  • Your login form needs XSRF protection too, even though the user has no session yet
    • You'll see this again with OAuth: The state parameter

Forging JSON With a Form

<form action="https://bank.com/api/transfer" method="post" enctype="text/plain">
  <input type="hidden" name='{"to": "attacker", "amount": 10000, "x": "' value='"}'>
</form>
  • A text/plain form sends name=value with no encoding
  • The body of this request:
    • {"to": "attacker", "amount": 10000, "x": "="}
    • Valid JSON! And it's a simple request, so there's no preflight
  • If your server parses the body as JSON without checking for Content-Type: application/json
    • The attack works, even though your front end only sends JSON with fetch

Clickjacking

  • The SOP stops a page from reading a cross-origin <iframe>, but not from embedding one
  • The attacker's page loads your real page in an invisible <iframe>
    • Positioned on top of a fake button: "Claim your free money!"
  • The user clicks the fake button
    • They actually clicked your real "Transfer" button
  • XSRF tokens don't help
    • The user submitted your real form, with the real token
  • Defense: Refuse to be framed
    • Content-Security-Policy: frame-ancestors 'self'
    • SameSite cookies also help: A cross-site iframe doesn't get Lax or Strict cookies

XSS Defeats XSRF Defenses

  • Recall HTML injection (XSS): The attacker's JavaScript runs on your origin
  • JavaScript running on your origin can:
    • Read your pages, including the XSRF token
    • Send same-origin requests that include your cookies
  • Every XSRF defense assumes the attacker's code runs on a different origin
  • Escape user-submitted content. Always

Other Protections

Checking Where Requests Come From

  • Browsers add headers that JavaScript can't set:
    • Origin - The origin of the page that sent the request (Sent on cross-origin requests and on POSTs)
    • Sec-Fetch-Site - same-origin, same-site, cross-site, or none (The user typed the URL)
  • On the server: Reject state-changing requests where Origin isn't yours, or Sec-Fetch-Site is cross-site
  • An attacker using curl can set any header, but then there are no victim cookies
  • Limitation: Older browsers, privacy extensions, and some proxies leave these headers out
    • A good extra layer, but not your only defense

Double-Submit Cookies

  • In practice, XSRF tokens are sometimes also stored in cookies
  • The server sets the XSRF token in a cookie (Not HttpOnly, so JavaScript can read it)
  • The page sends the same token in a form field or header
  • The server checks that the two values match. No need to store tokens on the server
  • Works because the attacker can't read the cookie (SOP), so they can't copy it into the form
    • The cookie is only where the token is stored. The proof is the copy in the body or header
  • Weakness: A subdomain can write cookies for your whole site
    • Fix: Sign the token with a server-side secret so it's tied to the user's session

Re-Authentication

  • For the most sensitive actions, require the user's current password:
    • Changing their password or email address
    • Disabling two-factor authentication
  • The attacker doesn't know the password, so they can't forge the request
  • A confirmation step or CAPTCHA works for high-value actions (eg. large transfers)
  • These hurt usability. Save them for the actions that matter most

Summary

XSRF Checklist

  • GET requests never change state
  • Set SameSite=Lax or SameSite=Strict on auth cookies. Explicitly
  • XSRF tokens on every request that changes state (Including login!)
    • Random, generated with secrets
    • Sent in a form field or header. Never only in a cookie
  • Only use CORS when you need it, and allow specific origins
  • Prevent XSS, or none of this matters
  • Refuse to be framed

Next Time: OAuth

  • Your app will accept requests that are designed to be cross-site
    • SameSite and the SOP can't help
  • The OAuth state parameter is an XSRF token
